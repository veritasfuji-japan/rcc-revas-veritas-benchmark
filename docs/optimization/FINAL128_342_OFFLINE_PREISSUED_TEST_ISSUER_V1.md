# #342 — Offline Preissued Test Issuer / Pinned Verifier Trust Anchor

## Rule of One

**INDEPENDENT_PREISSUED_TEST_VOUCHER_PINNED_TRUST_ROOT_NO_INPROCESS_SIGNATURE_MINTING**

Fix a public verification root **before** selecting a released RCC candidate. Require a separately preissued signed synthetic mandate to match the exact original RCC candidate and trusted test scope. Fail closed on wrong issuer, key, audience, signature, timestamp, case, actor, action, target, parameters, or scope.

This is a bounded **offline-signed synthetic fixture**, not a statement of an independently operated enterprise issuer, regulator, IAM provider, human approval, or production authorization.

## Why not just repeat #341?

#341 generated an Ed25519 signing key *during its runtime* and immediately trusted its own generated public key. That proves the cryptographic and native CDA / ExecutionIntent promotion mechanism under a controlled trust assumption; it does **not** prove an independently provisioned verifier trust root.

#342 removes test signer creation from the execution path. An Ed25519 signed fixture was created **before CI**, and only its signature, payload and verification public key are checked into this PR. The private signing key is **not committed**. No new signature is generated by the test code, and a candidate cannot provide its own trusted public key.

The fixture is signed over:
`b"VERITAS_RCC_OFFLINE_TEST_ISSUER_V1\\n" + canonical_json(payload)`

The issuer public key (Ed25519 raw 32 bytes), identity, key ID, audience, case ID, mandatory operation, validity period and fixture digests are pinned in `contracts/FINAL128_342_OFFLINE_PREISSUED_TEST_ISSUER_V1.json`.

This remains an **author-controlled test issuer fixture**; the verifier's source and the trusted key pin are part of the same repository. It does not prove organizational independence or separation of ownership. The private key is absent from the repository, but published test fixtures are not production grants. Production deployment must use an out-of-band managed trusted issuer, key rotation/revocation, audience and policy scoping, approval receipts and independent verification.

## Security and deployment limitations

- Signature verification provides key-possession evidence relative to the pinned public key, **not** business authorization.
- The key pin is code/repository-managed; there is no independently administered real-world issuer, secret manager, revocation status check, or organization-issued mandate.
- `required_human_approval=true` records the approval **requirement**, not a granted human approval.
- CI green, synthetic test-voucher acceptance or native schema promotability must never be represented as a live permission to execute.
- No real model calls, paid providers, bank operations, production IAM, Native v2 authorization, Bind consumption, reconciliation, scoring or external Effect.
- Historical V13 utility A=93/128, B=64/128, treatment injection success=0/128 remains an unmodified reference only.
