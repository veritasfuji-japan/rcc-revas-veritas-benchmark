# Ben synthetic Owner Approval enforcement in the existing isolated mock Custody — v0.1

**Research only / CI synthetic owner and issuer / pinned real VERITAS Bind / no real provider.**

## Scope

In an **opt-in CI mode** (\`--with-synthetic-owner\`) the existing
\`scripts/ci_mock_executor_authority_boundary_v1.py\` trusted Custody process
now enforces a root-enrolled synthetic Owner Approval **after issuer grant
verification and before inserting the durable single-use consumption row**.

1. Root CI harness makes a synthetic Ed25519 Owner key and signs the frozen mock
   request digest, exact operation, fixed synthetic scope and initial backend
   prestate digest. This is NOT real human approval. The key is separate from
   the existing issuer's UID-61105 key; Custody rejects key reuse.
2. The existing mock backend (UID 61103) serves a new state endpoint responding
   to a fresh 128-bit random challenge. It HMAC-protects the exact nonce, fixed
   operation, counter, revision and spent-record count with a shared mock
   transport secret, held only by backend and trusted Custody.
3. Custody (UID 61106) authenticates that status response, requires unspent
   backend state and checks the signed Owner Approval against the exact request
   **before** recording \`CONSUMED_UNKNOWN\` in the existing Custody SQLite store.
4. Custody then follows the pre-existing path: actual pinned VERITAS Bind
   in the trusted mock adapter, one authenticated synthetic HTTP \`/effect\`,
   backend consumption, mock effect receipt and Custody reconciliation.
5. The root CI supervisor intentionally corrupts the approval signature;
   the Agent→Executor→Custody path must deny it. The supervisor checks that
   both backend effect count and Custody consumption rows remain zero,
   then restores the approval and verifies one legitimate synthetic mock effect.

## Strong limitations

- This is a **test-mode integration** in the existing isolated mock Custody,
  **not the RCC/REVAS production adapter or actual Ben owner authority**.
  The synthetic Owner key is generated by the trusted root CI harness; different
  key bytes do not guarantee distinct independent parties.
- The backend and Custody share the HMAC key. Fresh reply authentication
  prevents spoofing/replay by parties without that key but **does not**
  independently prove the backend identity against a compromised Custody.
  The source trust anchor remains the trusted CI root/kernel and protected UIDs.
- The backend state is sampled **before** durable Custody consumption. It is
  not a global atomic lock across services. The existing Bind and backend
  independently recheck the expected target and preconditions; this test
  does not prove distributed consumption or eliminate all TOCTOU.
- Synthetic-owner mode currently supports **one normal run only**. Combined
  fault windows, owner revocation, trusted-clock expiry and concurrent owner
  consumption are intentionally rejected until independently tested.
- No real provider API endpoint, credentials, paid evaluation, banking action,
  fund transfer, production policy activation or human approvals are used.
  Normal mock workflows remain unchanged when the opt-in flag is omitted.
