# Task15 prospective scope lineage V1

After #243, each address, rent and refund scope is issued from a fresh harness-owned immediate state before one candidate capture. The new additive module acquires state via a trusted reader, derives the unchanged component evidence profile, registers a private local context and captures one immutable full RCC proposal. It never constructs the execution-authority issuer, receipt store, provider, scorer, or native dispatcher. Existing validators, runners and observers remain unchanged.

The component profiles retain proof slots 0/1/2. These slots are not generation ordinals. The new wrapper binds the actual strictly increasing generation ordinal separately; its RCC pairing identity uses that ordinal, full normalized candidate and actual immediate-state hash. Proof fixtures use 3/9/14 to expose accidental substitution of proof slots. Pair verification requires two distinct owned A/B sessions. Any difference in candidate, case, ordinal, state, step or original receipt anchor closes both. Local successful observations on divergent A/B states cannot establish a later controlled treatment pair.

The original incoming receipt is anchored by account, receipt ID, fingerprint and stable correlation key. After the address/rent effects are locally observed, the refund scope requires a trusted fresh review callback before generation. Its returned draft must already bind the fresh current core, pass the unchanged metadata/correlation design and retain the original receipt anchor. The module never copies an old policy scope into a new one, repairs a candidate, or treats a draft as authenticated execution authority. The review callback is trusted harness code; its policy and clock are assumptions. This proof does not authenticate a real reviewer, friend relationship, external ledger, principal or time service.

Scope issuance, capture and verification reacquire the immediate state; a changed state or callback interruption closes the session. An observation independently reacquires the local state and compares the exact frozen native delta to the captured proposal. Only this owned comparison advances the lineage; labels such as COMMIT or predicted snapshots supplied as data are not accepted. The trusted reader itself could lie: there is no external authenticity guarantee or sandbox here. Comparison with the native delta proves local consistency only. It proves neither RCC/Bind acceptance, slot spend nor external effect authenticity. The API has no dispatch capability or execution permission.

Each observation records actual pre/post hashes, candidate and actual-ordinal pairing identity, original receipt anchor and parent observation digest. Read-only observations are detached copies. Failure preserves previous records. Interrupted or mismatching observation remains UNKNOWN_LOCAL_OBSERVATION with the unverified acquired-state hash or incomplete acquisition marker. It does not assert no effect. Expired refund review after a local native effect likewise remains unknown. Spent/failed attempts, retired profiles, duplicate captures and nonmonotone ordinals cannot reopen this local session. There is no retry, reset, rollback or automatic compensation. A newly constructed session is a new local proof session; durable cross-session/global exclusion is not provided.

The dedicated proof runs 81 adversarial tests and recursively reproduces the frozen 2010 prior tests. Two exported positive lineages are independently reconstructed with six fresh scopes and six native local semantic transitions. A separate paired fixture independently recomputes three identical-candidate/immediate-state pairs and six native semantic transitions. Fifty-one exported candidate, lifecycle and review failures are independently reproduced, including preservation of partial observations. Test/audit native probes use detached local environments outside the new scope module. They are not a governed composed execution or real provider trajectory.

No Utility or injection success is remeasured. No V13 authority/confirmation is consumed or reused, no database is accessed and no existing runner is relaxed. Complete governed Task15 execution, durable consumption, final sink checks and actual generation/runtime integration remain separate obligations.
