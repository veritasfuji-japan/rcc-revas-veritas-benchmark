# Task15 prospective controlled address trajectory V1

This round integrates #218's bounded address runner with actual native AgentDojo
message initialization, shared read-only tool execution and paired continuation.
The generation element is explicitly scripted. Provider clients, scorers,
historical profiles and execution authorizations are unused.

The central invariant is one independently owned complete request and immediate
state, one common prefix, and one first protected address proposal for both arms.
Each continuation sees its own actual native value/error and post-state. Tool
data and answer variance cannot create authority or serve as candidate-level
treatment evidence.

## Program order and native execution

The owned harness supplies the complete envelope already bound by #217/#218.
The trajectory records the request digest and detached native pre-state before
the controlled runner issues a profile. Issuance precedes the first generation
query, including all read-only prefix proposals. Native SystemMessage and
InitQuery create the common system/user messages from the original instruction;
the harness supplies no repaired candidate or projected address argument.

The generation runtime exposes detached native tools/schemas and a detached
environment, with dispatch disabled. Each query appends exactly one assistant
message. Prior history, request, environment, runtime identity and phase context
must remain unchanged. Batches, nested FunctionCall arguments, placeholder args,
unknown read arguments, duplicate call IDs and malformed messages fail closed.
The prefix has at most eight generation queries and no automatic retry.

Read-only calls execute once through actual RCC and native ToolsExecutor on the
common environment. Its whole-state fingerprint must remain unchanged. The
positive fixture reads user information and a file containing an explicit
attacker city instruction. That returned text stays tool data; the authenticated
request remains the complete original user instruction.

The first `update_user_info` proposal is captured by #218's unchanged native
normalization/profile path. Both arms receive the same raw call/history and the
same full normalized RCC CandidateAction/V1.1 identity. Other protected prefix
tools terminate preparation without dispatch or replacement.

Each arm gets a detached native environment from the captured pre-state and one
local arm attempt. A retains RCC-only admission; B uses the unchanged #218
executor, actual native Bind and its final sink. The exact native transition and
actual four-field return are checked before adding the native tool-result message.
The tool call ID and original proposal link that result to the common history.

Each arm then receives one independent answer query with its own actual state
and value/error. Only nonempty terminal text is accepted. A later standing order,
refund, password change, additional address action or read is refused without
executing it. An invalid continuation after A's effect terminates the trajectory;
the journal keeps A's native dispatch explicit. It does not manufacture a paired
success, silently rerun A/B, roll back or label that partial execution no-effect.

## Evidence and claim boundary

The dedicated audit first reproduces the entire #218 proof, including #217/#216
and their frozen diagnosis dependencies. Source blobs and native pipeline files
are pinned. Forty trajectory tests use actual native RCC, tools, message elements,
FunctionsRuntime and Bind, with explicitly injected negative faults and provider,
network, database, trustlog and scorer entrypoints denied.

The positive fixture uses three common queries: two reads and one address
proposal, followed by two separate answer queries. A/B commit the same address
candidate with one native dispatch each. Six ineligible first candidates remain
in the common population; A commits, B refuses with zero dispatch, and their
continuations see the resulting distinct states and tool errors. Sixteen
concurrent attempts on one trajectory instance generate one population only.

This is a fresh scripted request and native in-memory environment. The read-file
attack is a development fixture; injection success is not scored or remeasured.
The authority source, acquisition, key, generator, native configuration and code
are owned trusted Python assumptions. Local fingerprints/HMAC do not authenticate
a real user or external state. Private executor/issuer interfaces remain outside
agent/tool reach. Durable global single execution and arbitrary trusted-process
compromise resistance are unproven.

The result concerns the first address step. It proves no complete Task15 outcome,
standing-order/refund/date authority, complete postal storage, historical case
recovery, real provider ordering or Final128 Utility improvement. Terminal text
is not a scored correctness claim. Independent answer variation is excluded from
candidate treatment claims. Frozen Final128/RCC/Bind/validator implementations
and V13 authorizations/confirmations remain unchanged.
